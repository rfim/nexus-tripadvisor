01 · The pathwhat runs in this repo

Kafka to the warehouse. Proven, not assumed.

Five steps from a tap in the app to a table an analyst, a model or an agent can trust. Every number on this page comes from the last run of the code in this repository.

01 · CAPTURE
Kafka

Three topics, – partitions, – records in a week. Offsets follow arrival, not event time.

02 · STREAM
Flink

Watermarks, idle partitions, an hour of allowed lateness, dedupe on id, a dead-letter topic. Python, and the same job on Apache Flink.

03 · CHECK
Spark

The nightly batch recomputes every window. – differences are left unexplained.

04 · PUBLISH
BigQuery

Partitioned by day, clustered by what consumers filter on. One contract renders the DDL, MERGE, policy tags and erasure; Snowflake too.

05 · WATCH
SLAs

Freshness from published completeness, error budgets, and an incident record that writes itself.

The stack, as the role lists it: Kafka → stream processing with Flink semantics (the job runs as Python and as a real Flink 1.20 job in Java, checked against each other) → Spark for batch → Snowflake and BigQuery for the warehouse, with SLAs, monitoring and root-cause work around all of it.
02 · Apache Flinkreal Apache Flink 1.20, run in CI · stated plainly

The stream, on Apache Flink.

The stream job is also an Apache Flink job: the DataStream API in Java 17, with keyed state, per-partition watermarks, allowed lateness and side outputs. CI builds it with Maven, replays the week on Flink's local MiniCluster, and fails if a window differs from the Python job.

03 · Apache Kafka · six problemsplanted in the topics, caught in the run

    
What Kafka really delivers. And what it takes.

      
The generator runs a travel site for a week and writes what the brokers would keep. It plants the six problems I've met running streams in production. Each one is tested, and each one is on the step-by-step page.

    

    
One review, version by version

    
A reviewer edits a review, then asks for their data to be erased. An outbox replay then re-sends the earlier edit with a new event id, so de-duplication can't catch it. Only the version rule does: the tombstone is version 4, and nothing older can bring the review back.

04 · BigQuery + Snowflakeone contract, two dialects, governance included

    
BigQuery-ready. Snowflake too.

      
Gold lands in BigQuery partitioned by day and clustered by the column consumers filter on, because you pay for bytes scanned. The DDL, MERGE, policy tags and erasure are generated from contracts/sources.yml, with the same for Snowflake, and committed; CI fails if they drift. Stated plainly: written and checked here, not run on a BigQuery project.

    

      
Same product: BigQuery, and Snowflake

      

    

    
Checked, not only rendered. The run loads Gold into SQLite with the same upsert semantics, runs the rules in contracts/quality.yml, applies the erasure, and checks that every personal field has a masking policy in Snowflake and a policy tag in BigQuery.

07 · Stream, then batchthe batch checks the stream; it doesn't replace it

    
Fast first. Right by morning.

      
The stream publishes within minutes and closes a window an hour after its watermark passes. The nightly batch recomputes every window from the whole topic, where nothing is late. Every window where they differ must be explained, record for record, by the stream's side output.

    

    

      
Windows that differ, and why
The offline upload: an iOS app flushed a flight's worth of events hours after they happened. The stream had closed those windows; the batch counts them.

      
Page views per hour, and the hour held
An hour is held from Gold when it is more than 2σ above the same hour on earlier days and at least double it. One hour was held; three users made 1,500 views in it.

    

  






  

    
08 · SLAsmeasured the way a consumer feels them

    
On time is a number. So is late.

      
A product's freshness is how far behind its published completeness is: the job publishes "complete up to" with the data, so an empty window at 3 a.m. still says the product is current. Samples every five minutes; the SLO turns them into an error budget.

    

    
partner_revenue_15m on Friday 9 October
Minutes behind, against the 45-minute SLA. A truncated record stopped the job at 14:05; freshness only crossed the line at 14:35. The restart count would have paged at 14:08.
